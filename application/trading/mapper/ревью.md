Ниже — сухой, подробный обзор того, что у вас уже есть по этой ветке, где узкие места, и что именно доделать, чтобы перейти к стабильной реализации (publish в Redpanda, последующая визуализация в Grafana).

Формат: **Наблюдения → Риски → Рекомендации → Конкретные действия/патчи**.

## 1) Протоколы (`market_event.proto`, Finam gRPC stubs)

### Наблюдения

* Контракт `MarketEvent` со схемой **Envelope + oneof payload** — корректный и масштабируемый.
* Используются числовые поля цен/объёмов как `double` в payload’ах (`QuoteEvent`, `TradeEvent`, `BarEvent`, `OrderBookLvl` и т. п.).
* Ранее были проблемы с импортом `google/type/decimal.proto` и зависимостями при `mvn compile`; после минимальных правок POM для `domain` сборка по *.proto пошла, но при генерации Java-классов указывались ссылки на `com.google.type.Decimal` (это ожидаемо, если исходные Finam-прото используют `google.type.Decimal`).

### Риски

* **Точность:** хранение цен/количеств в `double` может приводить к накоплению ошибок. Для пром-аналитики обычно используют `int64 amount` + `int32 scale` либо `string decimal`/`DecimalValue`.
* **Сходимость типов:** в Finam stubs входные значения — `google.type.Decimal` (строковое представление). Конвертация при маппинге обязательна, иначе вы будете упираться в `com.google.type` в домене.

### Рекомендации (минимально инвазивно)

* Оставить в **вашем типизированном контракте** `double` (как вы и решили), а **в мапперах** конвертировать из `google.type.Decimal → BigDecimal → double`. Вся логика — централизованно в `CommonProtoConverters`.
* Зафиксировать в Javadoc схем, что **точные расчёты PnL** выполнять **не на основе double**, а по репликации в хранилище с decimal/Decimal128 (ClickHouse/SQL).

### Что сделать

* Оставить `market_event.proto` как есть (typed).
* Убедиться, что **только** входные Finam stubs используют `google.type.Decimal`, а ваш `domain` — **нет**. Конвертация лежит в слое мапперов.

## 3) Ключи сообщений и партиционирование

### Наблюдения

* Принята стратегия ключей:

    * **Market data**: `tenant#board#code`
    * **Trading events**: `tenant#account#orderId`
    * **Portfolio**: `tenant#account`
* Есть `PartitionKeyService` с генерацией ключей и `Envelope` (EnvContext → EnvelopeFactory).

### Риски

* Неконсистентность при формировании `symbol`/`instrumentId` на разных путях (разные конвейеры → разный `symbol`).
* Неформализованная «маска» `tenant`/`board`/`code` → трудно диагностировать «перемешивание» разных сред (dev/stage/prod) в одном топике.

### Рекомендации

* Жёстко задать **инварианты** Envelope:

    * `symbol = code@board` (строго в таком формате всегда);
    * `event_ts ≤ ingest_ts`;
    * `tenant/environment` обязаны быть непустыми (либо заполнить `unknown` по умолчанию).
* В `PartitionKeyService` добавить **валидацию** и «normalize»: trim + toUpperCase для `board`, toUpperCase для `code` (если ваша нотация это допускает), нормализация `tenant`.

### Что сделать

* Доработать `PartitionKeyService` (микро-валидация и normalization).
* В `EnvelopeFactory` задать `nvl`-значения не пустыми строками, а предсказуемыми (`unknown`/`n/a`), чтобы на стороне потребителей не сломать фильтры по пустому значению.

## 4) MapStruct-мапперы и сборщик MarketEvent

### Наблюдения

* Базовый `@MapperConfig` (`BaseMapperConfig`) — есть.
* Общие конвертеры (`CommonProtoConverters`) — есть, содержат `Decimal → double` и `Timestamp → epochMillis`.
* `EnvContext`/`EnvelopeFactory` — есть и используются для сборки конверта.
* `MarketEventAssembler` — собирает oneof (правильный подход: oneof не через MapStruct).
* `OrderBookMappingSupport` и `MarketEventOrderBookMapper` — есть, решают нетривиальную задачу нормализации стакана (коалессация, сортировка, ограничение глубины, snapshot vs delta).

### Риски

* **OrderBook**:

    * при дельтах возможны строки с нулевыми размерами и `ACTION_UPDATE` — важна корректная интерпретация (оставлено в реализации через `applyAction`).
    * нет обработки «мусорных» уровней (отрицательные цены/объёмы → отбрасывать).
    * `sequence` берётся `0L`. В Finam иногда есть поле последовательности — если доступно, лучше проставлять для упорядочивания.
* **Quote/Trade/Bar**:

    * пока описаны как идея; желательно добавить явные интерфейсы `QuoteEventMapper`, `TradeEventMapper`, `BarEventMapper` (по образцу, который я давал ранее), чтобы вся схема typed-потоков была симметрична.

### Рекомендации

* В `MarketEventOrderBookMapper`:

    * отбрасывать уровни с **цена ≤ 0** или **size ≤ 0** до коалессации (safety-filter);
    * если в ваших Finam stubs есть `sequence` — проставлять его в `OrderBookEvent.sequence`;
    * оставить `coalesceByPrice=true` по умолчанию; это снижает «шум».
* Добавить **остальные мапперы** (`QuoteEventMapper`, `TradeEventMapper`, `BarEventMapper`) + простые unit-тесты на каждый.
* В `MarketEventAssembler` — один метод на каждый тип payload (как уже сделано для OB), плюс приватный метод «build env».

### Что сделать

* Принять предложенную реализацию стакана (у вас уже есть соответствующие файлы).
* Добавить недостающие мапперы для Quote/Trade/Bar (по шаблону; см. мои прежние примеры).
* Вынести **константные значения** `message_version`, `producer_id`, `source` в `@ConfigurationProperties`.

## 5) Публикация в Kafka (publisher, headers)

### Наблюдения

* Есть `KafkaMessagePublisher`, `KafkaHeaderUtils`, `MessagingProperties`.
* YAML-мапа тем обновлена: добавлены `finam.md.*`, `finam.trading.events.v1`, `finam.accounts.portfolio.v1`.
* Enum `Topic` очищен от дубликатов и дополнен новыми кодами.

### Риски

* Не всякие консьюмеры поддерживают бинарные protobuf-payload’ы по умолчанию — это нормально, но для отладки удобно иметь human-readable. В проде — только protobuf-value.
* Если в будущем подключите Schema Registry и Confluent/Redpanda Protobuf serializer — не забыть **SubjectNameStrategy** (`TopicNameStrategy`: `<topic>-value`).

### Рекомендации

* На прод публиковать **только** protobuf-value (без JSON).
* В headers класть: `message_id`, `message_version`, `trace_id`, `correlation_id`, `producer_id`, `source`, `schema_version` (ваша версия контракта).

### Что сделать

* Проверить, что `KafkaMessagePublisher` всегда использует **ключи** из `PartitionKeyService`.
* Убедиться, что **все** новые темы заведены в `application.yml` (и прокинуты через `MessagingProperties`) и соответствуют enum.

## 9) Мини-патчи (фрагменты, «как есть»)

**PartitionKeyService** — нормализация:

```java
private static String norm(String s) {
  if (s == null) return "unknown";
  var v = s.trim();
  return v.isEmpty() ? "unknown" : v;
}
public String mdKey(EnvContext ctx) {
  return String.join("#",
      norm(ctx.getTenant()),
      norm(ctx.getBoard()).toUpperCase(),
      norm(ctx.getCode()).toUpperCase());
}
```

**MarketEventOrderBookMapper** — фильтры до коалессации (добавить в `fillLevelsFromRows` перед `applyAction`):

```java
if (r.price.signum() <= 0) continue;
if (r.buySize.signum() < 0 || r.sellSize.signum() < 0) continue;
```

**EnvelopeFactory** — предсказуемые значения по умолчанию:

```java
private static String nvl(String v) { return (v == null || v.isBlank()) ? "unknown" : v; }
```

**Quote/Trade/Bar мапперы** — добавить по вашему пакету Finam (шаблон уже есть в предыдущем сообщении; просто вложите в `application/.../mapper`).
